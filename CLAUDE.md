# Tibia client reverse engineering

Target: `C:\Tibia\Tibia.exe`, the Tibia 7.x client (PE32, x86, MSVC 7.1 linker, built 2006-06-08,
sha256 `1a82fe97a39e536c29327d6d5dde316775f537dcc01506831429b1a0433b76f8`).
Data files next to it: `Tibia.dat`, `Tibia.spr`, `Tibia.pic`, `Tibia.cfg`.

## Reconstruction

Rebuilt sources are in `src/`; `notes/reconstruction.md` explains the process, tools and status.
Names go in `names.tsv`, settled file ranges in `file-ranges.tsv`; `symbols.tsv` and
`notes/source-map.md` are generated by `tools/triage.py`.

The decompilation workspace is not in the repository (since November 2, 2026; last commit with it:
e02adfa): `decomp/`, `rea-out/`, `names.tsv`, `symbols.tsv`, `file-ranges.tsv`, the analysis notes
(`notes/source-map.md`, `findings.md`, `Communication.md`, `Talk.md`) and the analysis tools (`tools/triage.py`,
`simplify.py`, `callcheck.py`, `ehinfo.py`, `ehcompare.py`, `xctable.py`, `lines.py`, `listing.cmd`). It is kept,
gitignored, in `decompilation/` with the same relative paths. Before analysis work run
`powershell -NoProfile -ExecutionPolicy Bypass -File tools\decompilation.ps1 -Restore` (back to the paths
above, still ignored); `-Stash` puts it away again. The build and the tests do not need it.

## Building

CMake presets, run from any shell through `python -I tools/build.py <workflow preset>` (it sets up MSVC with
vcvarsall.bat for the MSVC presets, then runs `cmake --workflow`): `oracle-x86` (the 32-bit oracle Patella.exe,
the four differential tests through CTest), `windows-x64` / `windows-x64-debug` (the x64 client Patella.exe, its
test build PatellaTest.exe with the virtual clock and scripted input of `notes/testmode.md`, the portable
libraries patella_core and patella_testmode, the unit tests and the 64-bit patcap.dll of compare_rendering.py),
`windows-x64-gcc` (patella_core and the unit tests with mingw-w64 GCC),
`linux-x64-gcc` / `linux-x64-clang` (patella_core and the unit tests with GCC 16 / Clang 22, the latter with
AddressSanitizer and UBSan; `-debug` for Debug). On Windows build.py runs the Linux presets in the Docker image
`patella-modern/linux-x64:gcc16.2-clang22.1` (build it once: `docker build -t
patella-modern/linux-x64:gcc16.2-clang22.1 docker/linux-x64`). `python -I tools/build.py --env <preset>
<command>` runs another command (`cmake --build --preset ...`, `ctest --preset ...`) in that environment. The
test server: `python -I tools/testserver.py start` / `stop`. Details: `notes/reconstruction.md`, "Building",
"Test server", "Checking".

The golden corpus (issue #24): `python -I tools/build.py --env oracle-x86 cmake --build --preset oracle-x86
--target golden_corpus` records it into `build/golden` (derived from Tibia.exe: local only, never committed,
pushed or uploaded); windows-x64's `golden_runner` (CTest test `golden`, skipped without a corpus) replays it
without Tibia.exe. Details: `notes/reconstruction.md`, "Checking", "The golden corpus".

## Code style

`.clang-format` describes the style of `src/` (tabs; `src/Extern` and `tools/` excluded by
`.clang-format-ignore`), `.editorconfig` the editor settings. Check with Visual Studio's clang-format
(`VC\Tools\Llvm\x64\bin`): `clang-format --dry-run --Werror src/*.cpp src/*.h src/compat/*.h src/testmode/*.cpp
src/testmode/*.h src/res/resource.h tests/unit/*.cpp
tests/golden/*.cpp tests/golden/*.h`.
Run clang-tidy only through `python -I tools/tidy.py -p <build dir with compile_commands.json> [--fix] <files>`,
never `clang-tidy --fix` directly: until M5 no change may touch the arguments of TASSERT*, TERROR* or TEND*
(stringized into the messages difftest compares), and the wrapper reverts every fix inside them. The product
targets' compiler, warning and hardening settings are `cmake/Warnings.cmake` and `cmake/Hardening.cmake`;
the oracle-x86 preset never uses them. Details: `notes/reconstruction.md`, "Checking".

## CI

`.github/workflows/hosted.yml` (GitHub's runners, also on pull requests): windows-x64 with MSVC x64 and
`-DPATELLA_CLIENT=OFF`, linux-x64-gcc and linux-x64-clang in the image of `docker/linux-x64`, clang-format, and
clang-tidy against the findings baseline `tools/tidy-baseline.tsv` (no new findings). A change that adds a finding
fixes it or rewrites the baseline in the image: `python -I tools/build.py --env linux-x64-clang bash -c "cmake
--preset linux-x64-clang && python3 -I tools/tidy.py -p build/linux-x64-clang --all --write-baseline
build/linux-x64-clang/tidy-baseline.tsv"`, then copy it to `tools/`. `.github/workflows/self-hosted.yml` (oracle-x86,
the comparisons; this machine) runs only on push and workflow_dispatch, and only when the repository variable
`PATELLA_SELF_HOSTED` is `true`. Details: `notes/reconstruction.md`, "Checking".

## REA

The `rea` MCP server (https://github.com/morluto/rea) is registered at Claude Code local scope for this
folder only, with the skill in `.claude/skills/reverse-engineer-anything`. Pass `C:\Tibia\Tibia.exe` as
the target to its native analysis tools.

- Package: `C:\Servers\Software\rea` (rea-agents 6.8.0), CLI: `rea` (`C:\Servers\Software\rea\rea.cmd`)
- Runtime: portable Node 24.22.2 in `C:\Servers\Software\node` (the system Node is too old for REA)
- Provider: Ghidra 12.1.4 in `C:\Servers\Software\ghidra_12.1.4_PUBLIC`, JDK 24 (`C:\Program Files\Java\jdk-24`),
  `REA_ANALYSIS_PROVIDER=ghidra`. The older Ghidra 11.4.2 in `C:\Servers\Software\Ghidra` is not supported by REA.
- Windows Ghidra support is read-only: function renames and comments are not available.
- A full import takes about 80 s; Ghidra finds about 21,700 functions and 3,200 strings.

CLI examples (`rea.cmd` sets `GHIDRA_INSTALL_DIR` and `JAVA_HOME` itself if they are unset):

```
rea analyze C:\Tibia\Tibia.exe --provider ghidra --json
rea search C:\Tibia\Tibia.exe "Tibia.spr" --provider ghidra --json
rea decompile C:\Tibia\Tibia.exe 0x401000 --provider ghidra --json
```

To update: `rea update` does not refresh the local-scope registration. Run
`npm install --prefix C:\Servers\Software\rea rea-agents@latest` with the portable Node, then copy the
skill again from `node_modules\rea-agents\skills`.
