The machine's folders (since November 4, 2026; `notes/reconstruction.md`, "The machine's folders"): this

## Reconstruction

Rebuilt sources are in `src/`; `notes/reconstruction.md` explains the process, tools and status.
Names go in `names.tsv`, settled file ranges in `file-ranges.tsv`; `symbols.tsv` and
`notes/source-map.md` are generated by `tools/triage.py`.

The decompilation workspace is not in the repository (since November 2, 2026; last commit with it:
e02adfa): `decomp/`, `rea-out/`, `names.tsv`, `symbols.tsv`, `file-ranges.tsv`, the analysis notes
(`notes/source-map.md`, `findings.md`, `Communication.md`, `Talk.md`) and the analysis tools (`tools/triage.py`,
`simplify.py`, `callcheck.py`, `ehinfo.py`, `ehcompare.py`, `xctable.py`, `lines.py`, `listing.cmd`). It is kept,
gitignored, in `decompilation/` with the same relative paths. Before analysis work run
`powershell -NoProfile -ExecutionPolicy Bypass -File tools\decompilation.ps1 -Restore` (back to the paths
above, still ignored); `-Stash` puts it away again. The build and the tests do not need it.

## Building

CMake presets, run from any shell through `python -I tools/build.py <workflow preset>` (it sets up MSVC with
vcvarsall.bat for the MSVC presets, then runs `cmake --workflow`): `oracle-x86` (the 32-bit oracle Patella.exe,
the four differential tests through CTest), `windows-x64` / `windows-x64-debug` (the x64 client Patella.exe, its
test build PatellaTest.exe with the virtual clock, scripted input and dumps (state, packets, frames) of
`notes/testmode.md`, the portable
libraries patella_core and patella_testmode, the unit tests and the 64-bit patcap.dll of compare_rendering.py),
`windows-x64-asan` / `windows-x64-asan-debug` (windows-x64 under MSVC's AddressSanitizer, `/fsanitize=address`: the
client, PatellaTest.exe, golden_runner and the unit tests, issue #70; the ASan runtime DLL is copied next to each
executable), `windows-x64-gcc` (patella_core and the unit tests with mingw-w64 GCC),
`linux-x64-gcc` / `linux-x64-clang` (patella_core and the unit tests with GCC 16 / Clang 22, the latter with
AddressSanitizer and UBSan; `-debug` for Debug). Every preset also compiles each header of src/ on its own
(`cmake/HeaderCheck.cmake`, issue #49: the `header_check_*` object libraries, a generated one-line source per
header with a target's settings; a new header goes on one of its lists, or the configure fails). On Windows build.py runs the Linux presets in the Docker image
`patella-modern/linux-x64:gcc16.2-clang22.1` (build it once: `docker build -t
patella-modern/linux-x64:gcc16.2-clang22.1 docker/linux-x64`). `python -I tools/build.py --env <preset>
<command>` runs another command (`cmake --build --preset ...`, `ctest --preset ...`) in that environment. The
test server: `python -I tools/testserver.py start` / `stop`. Details: `notes/reconstruction.md`, "Building",
"Test server", "Checking".
The x64 client's only engine is the Vulkan engine, as engine 2 (issues #19, #20, `notes/vulkan.md`; DirectDraw,
Direct3D 9 and OpenGL only in oracle-x86); its device is the advanced graphics options' choice (issue #31: "Automatic",
"GPU", "CPU" in the engine buttons' places), stored as `Device` in `Patella.ini` next to Tibia.cfg (the fork's own
settings file, `src/settings/`), and `PATELLA_VULKAN=auto|gpu|gpuN|cpu` in its environment overrides it at start-up
(the comparisons' and tests' choice; `notes/vulkan.md`, "Choosing the device"); its pinned libraries and the CPU
driver (Mesa's lavapipe, copied next to
the executables) come with the first configure of windows-x64 (`cmake/Vulkan.cmake`); `tests_vulkan` checks it
headless.

The reference recordings (issue #23, M2's exit; `notes/testmode.md`, "Reference recordings"): `python -I
tools/reference.py record --reference C:\Tibia\Patella-Modern\build\reference` (Windows, Tibia.exe under patcap.dll;
the test server only for the two live recordings) and `python -I tools/reference.py compare --reference
C:\Tibia\Patella-Modern\build\reference` (PatellaTest.exe on each session, the server side replayed inside the client,
no server, PATELLA_VULKAN=cpu; Python only). Also as `record`/`compare` first words of compare_traffic.py,
compare_files.py and compare_rendering.py. Local CipSoft-derived data: never committed, pushed or uploaded.
The live checks run on the desktop of the session that starts them; a second interactive session (another Windows
user, kept connected and unlocked) keeps the user's input away (issue #56; notes/reconstruction.md, "Checking").
`--hidden` (tools/desktop.py) is experimental: DirectDraw, Direct3D 9, the CPU driver and GetCursorPos fail there.

The golden corpus (issue #24): `python -I tools/build.py --env oracle-x86 cmake --build --preset oracle-x86
--target golden_corpus` records it into `build/golden` (derived from Tibia.exe: local only, never committed,
pushed or uploaded); windows-x64's `golden_runner` (CTest test `golden`, skipped without a corpus) replays it
without Tibia.exe. Details: `notes/reconstruction.md`, "Checking", "The golden corpus".

## Code style

`.clang-format` describes the style of `src/` (tabs; `src/Extern` and `tools/` excluded by
`.clang-format-ignore`), `.editorconfig` the editor settings. Check with Visual Studio's clang-format
(`VC\Tools\Llvm\x64\bin`): `clang-format --dry-run --Werror src/*.cpp src/*.h src/compat/*.h src/types/*.h src/testmode/*.cpp
src/testmode/*.h src/vulkan/*.cpp src/vulkan/*.h src/settings/*.cpp src/settings/*.h src/res/resource.h tests/unit/*.cpp tests/vulkan/*.cpp
tests/golden/*.cpp tests/golden/*.h`.
The Microsoft CRT's and compiler's own spellings (`_snprintf`, `_stricmp`, `__cdecl`, `#pragma warning`...) go
through `src/compat/msvc.h` and `msvc_io.h` (issue #43), which keep their semantics on every platform.
Run clang-tidy only through `python -I tools/tidy.py -p <build dir with compile_commands.json> [--fix] <files>`,
never `clang-tidy --fix` directly: until M5 no change may touch the arguments of TASSERT*, TERROR* or TEND*
(stringized into the messages difftest compares), and the wrapper reverts every fix inside them. `--headers` runs
misc-include-cleaner on each header of the build's header checks as its own main file (issue #49); an include kept
for the images or that include-cleaner cannot see used says `// IWYU pragma: keep` with the reason. The product
targets' compiler, warning and hardening settings are `cmake/Warnings.cmake` and `cmake/Hardening.cmake`;
the oracle-x86 preset never uses them. Details: `notes/reconstruction.md`, "Checking".

## CI

`.github/workflows/hosted.yml` (GitHub's runners, also on pull requests): windows-x64 with MSVC x64 and
`-DPATELLA_CLIENT=OFF`, windows-x64-asan's unit tests (Release, `-DPATELLA_CLIENT=OFF`, issue #70), the client's and the test build's sources compiled without Tibia.exe
(`-DPATELLA_CLIENT_COMPILE_ONLY=ON`, targets `Patella_compile` and `PatellaTest_compile`, issues #25, #46, and
their headers alone, `header_check_client` and `header_check_test_build`, issue #49), linux-x64-gcc and linux-x64-clang in the image of `docker/linux-x64`, clang-format, the grep gate `python -I tools/banned_calls.py` (no strcpy, strcat, sprintf, vsprintf or gets in src/; the buffers are `TFixedString`/`TStringBuffer` of `src/types/FixedString.h`, issue #57), and
clang-tidy against the findings baseline `tools/tidy-baseline.tsv` (no new findings; `--all --headers`; `--zero bugprone-`: no
bugprone-* finding at all, issue #63). Static analysis of patella_core (issue #63, `cmake/Core.cmake`): the windows-x64 builds
compile it with MSVC `/analyze`, linux-x64-gcc (and windows-x64-gcc) with GCC `-fanalyzer`; a finding fails the build like a
warning. A finding of any of the three is fixed or suppressed in the code with its reason and a row in notes/decisions.md's
table ("Static analysis of the core library"). `python -I tools/tidy_ci.py`
runs that job locally (the commit's image, files and script; `--worktree` for uncommitted changes, `--hosted <run id>`
compares with a hosted run) and reports exactly what it reports: run it before pushing. The per-target Windows runs
(Visual Studio's clang-tidy) still check the code Linux does not compile, and miss findings the image reports
(issue #51: MSVC's `std::size_t` hides locals from misc-const-correctness). A change that adds a finding
fixes it or rewrites the baseline in the image: `python -I tools/build.py --env linux-x64-clang bash -c "cmake
--preset linux-x64-clang && python3 -I tools/tidy.py -p build/linux-x64-clang --all --write-baseline
build/linux-x64-clang/tidy-baseline.tsv --zero bugprone-"`, then copy it to `tools/`. `.github/workflows/self-hosted.yml` (oracle-x86,
the comparisons and testmode_check.py; this machine) runs only on push and workflow_dispatch, and only when the repository variable
`PATELLA_SELF_HOSTED` is `true`. Details: `notes/reconstruction.md`, "Checking".

## REA

The `rea` MCP server (https://github.com/morluto/rea) is registered at Claude Code local scope for this
folder only, with the skill in `.claude/skills/reverse-engineer-anything`. Pass `C:\Tibia\Patella\Tibia.exe` as
the target to its native analysis tools.

- Package: `C:\Servers\Software\rea` (rea-agents 6.8.0), CLI: `rea` (`C:\Servers\Software\rea\rea.cmd`)
- Runtime: portable Node 24.22.2 in `C:\Servers\Software\node` (the system Node is too old for REA)
- Provider: Ghidra 12.1.4 in `C:\Servers\Software\ghidra_12.1.4_PUBLIC`, JDK 24 (`C:\Program Files\Java\jdk-24`),
  `REA_ANALYSIS_PROVIDER=ghidra`. The older Ghidra 11.4.2 in `C:\Servers\Software\Ghidra` is not supported by REA.
- Windows Ghidra support is read-only: function renames and comments are not available.
- A full import takes about 80 s; Ghidra finds about 21,700 functions and 3,200 strings.

CLI examples (`rea.cmd` sets `GHIDRA_INSTALL_DIR` and `JAVA_HOME` itself if they are unset):

```
rea analyze C:\Tibia\Patella\Tibia.exe --provider ghidra --json
rea search C:\Tibia\Patella\Tibia.exe "Tibia.spr" --provider ghidra --json
rea decompile C:\Tibia\Patella\Tibia.exe 0x401000 --provider ghidra --json
```

To update: `rea update` does not refresh the local-scope registration. Run
`npm install --prefix C:\Servers\Software\rea rea-agents@latest` with the portable Node, then copy the
skill again from `node_modules\rea-agents\skills`.
