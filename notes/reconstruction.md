# Reconstruction guide

How a source file of Tibia.exe 7.72 is turned into `src/<File>.cpp`. `src/Network.cpp` is the
reference example.

## Inputs

Since November 2, 2026 the decompilation workspace below (`symbols.tsv`, `names.tsv`, `file-ranges.tsv`,
`decomp/`, `notes/source-map.md`, the analysis tools triage.py, simplify.py, callcheck.py, ehinfo.py,
ehcompare.py, xctable.py, lines.py, listing.cmd, and `rea-out/`) is not in the repository: it is kept,
gitignored, in `decompilation/`; `tools\decompilation.ps1 -Restore` puts it back at these paths before
analysis work, `-Stash` puts it away (CLAUDE.md). The last commit that has the files is e02adfa.

| File | What it is |
|---|---|
| `symbols.tsv` | Every function: address, size, kind, source file, assertion lines, catch-block parent, parameter names. Generated by `tools/triage.py`. |
| `names.tsv` | Hand-maintained names: address, name, kind, confidence, note. Add a row for every function you name. |
| `decomp/clean/<File>.c` | Readable pseudocode for one source file. Generated by `tools/simplify.py`; rerun it after editing `names.tsv`. |
| `decomp/raw/functions/<address>.c` | Raw Ghidra output, when the clean copy hides something. |
| `notes/source-map.md` | Which functions belong to which file, and the unresolved gaps. |

Regenerate after changes: `python -I tools/triage.py` (only when the raw decompile changes), then
`python -I tools/simplify.py`.

## Reading the clean pseudocode

- `TASSERT_FAILED(line, "expr", "name", value)`: a failed `TASSERT1(line, expr, name)`.
  The expression text is the original source text; the line is the macro's first argument (issue #35).
- `TERROR(line, "message", "name", value)`: `TERROR1(line, "message", name)`.
- After most functions come three catch blocks. A 20-byte one re-throws a `PROGRAM_ERROR`; a
  `TRETHROW(line, "names"...)` one and a `TERROR(line, "unknown exception occurred", ...)` one
  are `TEND(line)`, `TEND1(line, name)` or `TEND2(line, a, b)`, closing a `TBEGIN` at the start of
  the body. The names are the function's parameters (or expressions of them). `python -I tools/lines.py
  check` checks every site's line against the binary.
- A catch block with its own message, such as "Symmetric encryption failed with unknown
  exception", is an inner `try { ... } catch (...) { TERROR("..."); }`.
- Get the catch types and the try ranges from the exception tables, not from the pseudocode:
  `python -I tools/ehinfo.py <address>`. The standard trio is `PROGRAM_ERROR`, `TMyException &`,
  `...`. If the `TBEGIN` try block starts at a state above 0 (for example `try states 5-5`), the
  assertions that build the first states come **before** `TBEGIN`; a failure there is not wrapped
  with "exception occurred". Each assertion builds five strings, so five states.
- Ghidra hides the `this` pointer of member calls (`in_ECX`). When it matters which object a
  call uses, read the instructions: `rea instructions C:\Tibia\Tibia.exe <address> --provider
  ghidra --snapshot C:\Tibia\rea-out\tibia.snapshot --json` and look for `MOV ECX, <address>`
  or `LEA ECX, [EBP + ...]` before the call.
- Return values of small wrappers are often dropped by Ghidra (`void FUN_...` that returns
  `EAX` from a callee). Check the callers.
- Inlined string functions appear as copy loops (`strcpy`, `strcat`, `strlen`, `memset`).
- Static constructors are not found by Ghidra. They sit near `0x559fc0`; disassemble them with
  `objdump -d -M intel --start-address=0x559fc0 --stop-address=0x55a400 Tibia.exe`.

## Writing the source

- One `src/<File>.cpp` and `src/<File>.h` per original file, with the original file name.
- Functions in original source order: sort by assertion and catch line numbers, not by address.
  Functions without line evidence go where the binary puts them.
- Before each function: `// 0x<address>, lines <first>-<last>` and a short note only when the
  behaviour is not obvious.
- Names: keep every name the binary gives (parameter names from catch blocks, identifiers in
  assertion strings such as `CurrentServer`, `NUMBEROFSERVER`). Invent names only for the rest,
  in the original style: TitleCase free functions, `T`-prefixed classes, TitleCase members.
- Globals: `static` unless another file uses them, ordered by address, each with its address.
- Every file is reconstructed, so every declaration lives in the header of the file that defines
  it (`src/external.h` held the declarations of files not reconstructed yet; it was removed in
  issue #14). A new declaration goes into its owner's header with its address; a header includes
  the headers whose types it uses, a .cpp the headers of the functions and data it uses (no
  catch-all header). Watch the include cycles noted in notes/progress.md.
- Data defined in a header with internal linkage has one copy per including object in the binary:
  the text table (`src/Text.h`, every .cpp that reads a text includes it; Dialogs.h too, for its
  inline code) and graphics.h's DefaultFontColor. An object's code reads only its own copy.
- Use the error macros from `src/common.h` (`TASSERT*`, `TERROR*`, `TBEGIN`/`TEND*`) exactly where
  the binary has the corresponding blocks.
- Behaviour must match the binary exactly, including odd behaviour (for example
  `ConnectToGameServer` connects even when `CreateSocket` failed). Note such cases in a
  comment; do not fix them.
- Tabs for indentation.

## Building

The build is CMake (3.30 or newer) with Ninja: `CMakeLists.txt`, `CMakePresets.json`, `cmake/*.cmake`. The
MSBuild project (`Patella.sln`, `Patella.vcxproj`) and the .cmd/.ps1 scripts are gone since issue #10; every
step they did is a CMake target, a CTest test or a Python tool now (notes/decisions.md, "Removing the Visual
Studio project and the scripts (issue #10)"). The MSVC presets mark their architecture and toolset
`external`: CMake does not set up the compiler. `tools/build.py` does it (vcvarsall.bat for the preset's
architecture, found through vswhere) and runs the workflow, from any shell:

```
python -I tools/build.py oracle-x86              # configure, build Release, run the four tests through CTest
python -I tools/build.py windows-x64             # the x64 client and the unit tests, Release
python -I tools/build.py windows-x64-debug       # the same, Debug
python -I tools/build.py windows-x64-gcc         # the unit tests with mingw-w64 GCC 16 (-debug: Debug)
python -I tools/build.py linux-x64-gcc           # patella_core and the unit tests, GCC 16 (Docker on Windows)
python -I tools/build.py linux-x64-clang         # the same, Clang 22 with ASan and UBSan (-debug: Debug)
python -I tools/build.py --list                  # the workflow presets
python -I tools/build.py oracle-x86 --fresh      # extra options go to cmake --workflow
python -I tools/build.py --env oracle-x86 cmake --build --preset oracle-x86-debug   # any command, in the
python -I tools/build.py --env oracle-x86 ctest --preset oracle-x86 -R vlongtest    # preset's environment
```

No warnings on any preset (plan section 4.1): the product presets build with /WX or -Werror, and the oracle,
which keeps the former Patella.vcxproj's /WX-, is failed by `tools/build.py` instead (issue #17). It passes
cmake's output through and scans it, up to the test step, for compiler, resource compiler, assembler and linker
warnings (MSVC's `warning C4101`, `warning LNK4075`, `warning RC4005`, `warning A4018`, `Command line warning
D9025`; GCC's and Clang's `file:line:col: warning:`); after a run that warned it lists them again (`build.py: 1
warning in the build ...`) and exits 1, even when cmake succeeded. That holds for every workflow and for `--env
<preset> cmake ...`. Ninja compiles only what changed, so an up-to-date build shows no warnings; `--fresh`
checks every file. Plain `cmake --workflow` from a developer prompt does not check.

From a developer prompt for the right architecture (`vcvarsall.bat x86` or `x64`) the plain CMake commands do
the same: `cmake --workflow --preset <name>`, or step by step `cmake --preset oracle-x86`, `cmake --build
--preset oracle-x86` (oracle-x86-debug: Debug), `ctest --preset oracle-x86`. Everything needs Visual Studio
2026 with the C++ workload and the MFC component (MSVC 14.51), Python 3.13 on PATH and Tibia.exe in the root
(or the cache variable PATELLA_TIBIA_EXE): the resource pictures are extracted from it at configure time
(cmake/Resources.cmake, notes/resources.md).

The preset `oracle-x86` (issue #4; `cmake/OracleX86.cmake`) is a test instrument until M6. It writes
build\oracle-x86\<Configuration>:

- Patella.exe, the reconstructed client, with exactly the compiler, resource compiler and linker options of
  the former Patella.vcxproj (issue #16): every `src/*.cpp`, `src/Extern/regexp/*.c` and `src/res/Patella.rc`
  for x86 with static MFC (nafxcw.lib) and the static CRT (`/MT`), Tibia.exe's system libraries with
  oleacc.dll delay-loaded, no manifest; a PDB in both configurations. One exception: SurfaceGL.cpp compiles
  without `/FC`, which would make the name in glh_extensions.h's `#line 173 "Extern\\glh/glh_extensions.h"`
  absolute, so the malloc-failure message prints the original's `Extern\glh/glh_extensions.h` (issue #14; the
  x64 build and the test programs have no /FC at all). After every link the build checks the
  resources against Tibia.exe (`tools/compare_resources.py`, 0 differences; a difference fails the build).
  `python -I tools/compare_imports.py Tibia.exe build\oracle-x86\Release\Patella.exe` compares the import
  tables. Details: notes/decisions.md, "Building Patella.exe (issue #16)", "CMake: the oracle-x86 preset
  (issue #4)" and "/FC and the glh_extensions.h #line name (issue #14)".
- The four test programs difftest, sysinctest, communicationtest and vlongtest with the options of the former
  tools\difftest\build.cmd (the same in every configuration), which `ctest --preset oracle-x86` runs ("Checking"
  below). The tests get Tibia.exe as their argument and a private TEMP each (build\oracle-x86\tmp\<test>).
- patcap.dll, the 32-bit capture DLL of tools/compare_rendering.py for Tibia.exe and the oracle's Patella.exe
  (`cmake/Capture.cmake`; the script builds the target itself when the DLL is missing or older than
  tools/capture/patcap.c).
- mfc_shim_check: every source of Patella.exe compiled, not linked, against `src/compat/mfc_shim.h` instead of
  MFC (the former `compile-check.cmd` with TIBIA_MFC_SHIM set; "Checking" below).

The product presets (windows-x64, issue #5; linux-x64-gcc and linux-x64-clang, issue #7) give their targets
the settings of `cmake/Warnings.cmake` and `cmake/Hardening.cmake` (issue #8), which the oracle never uses:

- `patella_target_language(<target>)`: C++23 (`/std:c++latest` on MSVC, `-std=c++26` on GCC and Clang),
  `/permissive- /Zc:__cplusplus /utf-8 /Zc:preprocessor /Zc:inline`, no `/Zc:strictStrings-`; C17 for the C
  sources on GCC and Clang (the regexp's K&R definitions are not C23, GCC 16's default).
- `patella_target_warnings(<target>)`: `/W4` (GCC and Clang `-Wall -Wextra -Wpedantic -Wconversion
  -Wshadow`) per source, `/W3` (`-Wall`) for the files on the compiler's baseline list in Warnings.cmake
  (`PATELLA_WARNING_BASELINE_MSVC`, `_GCC`, `_CLANG`; a file is on a list when its translation unit warns,
  wherever the warning is), and warnings as errors (`COMPILE_WARNING_AS_ERROR`; `cmake
  --compile-no-warning-as-error` turns it off to measure). Headers in angle brackets are external to MSVC
  (`/external:anglebrackets /external:W0`). Clang's warning about K&R definitions
  (`-Wdeprecated-non-prototype`, on at every level) is off for C. A file leaves a list when it builds clean at
  the full level; the lists only shrink.
- `patella_target_hardening(<target>)`: `/guard:cf /CETCOMPAT`; `-fstack-protector-strong`,
  `_FORTIFY_SOURCE=3` (optimised builds), `_GLIBCXX_ASSERTIONS` (Debug), PIE and, on Linux, full RELRO; with
  the cache variable `PATELLA_SANITIZE` (GCC and Clang; linux-x64-clang sets `address,undefined`)
  `-fsanitize=<list> -fno-sanitize-recover=all -fno-omit-frame-pointer`, so every finding fails the test.

`patella_core` (`cmake/Core.cmake`, issue #7) is the static library of the code that is already portable,
built by every product preset: vlong.cpp, TRSA.cpp, TXTEA.cpp, TMyException.cpp, Utils.cpp, Skins.cpp,
src/Extern/regexp/regexp.c and the header-only Container.h. It defines `PATELLA_CORE`, which keeps MFC and the
Windows headers out of common.h, so no core source can use them. The client and the oracle still compile these
sources themselves, with MFC. Its tests are `tests_core` (tests/unit/core_*.cpp; the expected values that are
not the code's own come from `tests/unit/core_expected.py`, Python's exact integers and doubles).

The Linux presets `linux-x64-gcc` (GCC 16) and `linux-x64-clang` (Clang, with AddressSanitizer and UBSan),
each with a `-debug` workflow, build patella_core and the unit tests, not the client (PATELLA_CLIENT is OFF; the
client needs Tibia.exe for its resources, and MFC). On Linux: `cmake --workflow --preset linux-x64-gcc`. On
Windows, `python -I tools/build.py linux-x64-gcc` (and `--env linux-x64-gcc <command>`) runs them in the Docker
image `patella-modern/linux-x64:gcc16.2-clang22.1` (docker/linux-x64/Dockerfile: Docker Hub's gcc:16.2.0-trixie
pinned by digest, Debian's Clang 22.1.8, CMake 3.31.6 and Ninja 1.12.1 pinned by version, since issue #11
also clang-format and clang-tidy 22.1.8; build it once with
`docker build -t patella-modern/linux-x64:gcc16.2-clang22.1 docker/linux-x64`, about half a minute, and again
when the Dockerfile changes: the tag stays the same). build.py
mounts the repository read-only, copies the files git knows (tracked, and untracked ones that are not ignored:
never the CipSoft files) with their times to the container's case-sensitive /work and runs there;
build\<preset> is mounted as /work/build/<preset>, so the build tree and doctest stay. Details:
notes/decisions.md, "The Linux presets and patella_core (issue #7)".

The unit tests (`tests/unit/`, doctest 2.5.3: an installed one through find_package, otherwise downloaded once
by FetchContent and checked against its SHA256; issue #9) build with the presets windows-x64 (MSVC x64; it
builds the client too, below), windows-x64-gcc (mingw-w64 GCC 16 on PATH, which builds nothing else) and the
Linux presets (above):

```
python -I tools/build.py windows-x64         # configure, build Release, run the unit tests through CTest
python -I tools/build.py windows-x64-debug   # the same for Debug
python -I tools/build.py windows-x64-gcc     # (and windows-x64-gcc-debug); cmake --workflow --preset works too
```

They write build\<preset>\tests\unit\<Configuration>: `tests_unit` (src/compat/cxx26.h as the compiler selects
it: the stand-ins on MSVC and on Clang 22 with libstdc++ 14, contract_assert and std::inplace_vector on GCC 16)
and `tests_unit_cxx26_standin` (the same tests with PATELLA_CXX26_STANDIN), each a CTest test, plus one per
contract violation scenario (RunContractViolation.cmake), `tests_core` and, since Patella-Modern issue #21,
`tests_testmode` (the test mode's clock, script parser and scheduler; below). The mingw executables get the
compiler's runtime DLLs copied next to them.
src/compat/cxx26.h is the only way to C++26 features (plan section 8): `CONTRACT_ASSERT(Predicate)` and
`patella::TStaticVector<T, N>` so far; its comment lists what the stand-ins do not reproduce. Details:
notes/decisions.md, "src/compat/cxx26.h and the unit tests (issue #9)".

Since issue #5 the preset windows-x64 also builds the client for x64 (`cmake/WindowsX64.cmake`): today's code
with static x64 MFC and the original engines (DirectDraw, Direct3D 9, OpenGL), the oracle's sources,
definitions, import libraries and linker options (no manifest, oleacc.dll delay-loaded), with the product
settings of Warnings.cmake and Hardening.cmake, 0 warnings with /WX in Release and Debug.
`python -I tools/build.py windows-x64` builds Release and runs the unit tests; `python -I tools/build.py
windows-x64-debug` does the same for Debug. The result is `build\windows-x64\<Configuration>\Patella.exe` with its
`Patella.pdb` (a PDB in both configurations, which client_state.py's PDB offsets need). Its resource pictures are
extracted from Tibia.exe into build\windows-x64\res at configure time, as for the oracle
(cmake/Resources.cmake, shared); without Tibia.exe the configure stops, and `-DPATELLA_CLIENT=OFF` builds only the unit tests
and patcap.dll. The preset also builds the 64-bit patcap.dll, `build\windows-x64\<Configuration>\patcap.dll`, with or
without the client (`cmake/Capture.cmake`, issue #18): compare_rendering.py loads it into the x64 Patella.exe. The
original's structure layouts hold only in the 32-bit build: the static_asserts that check a size or offset which
pointers change are inside `#if PATELLA_ORIGINAL_LAYOUT` (common.h, x86 only). Details: notes/decisions.md,
"Windows x64 build (issue #5)".

Next to it the preset builds `PatellaTest.exe` (Patella-Modern issue #21; option `PATELLA_TEST_BUILD`, default
ON), the test build: the same sources with `PATELLA_TEST_MODE`, plus src/testmode (the virtual clock and the
input script; cmake/TestMode.cmake's `patella_testmode` is their portable part, built by every product preset
and tested by `tests_testmode`). The hooks it needs in the client (src/TestHooks.h) are the system calls
themselves in Patella.exe and the oracle, whose images are unchanged by them (pecompare; notes/decisions.md,
"Test mode: virtual clock and scripted input (Patella-Modern issue #21)"). `PatellaTest.exe --test-script
<file>` plays a script of keyboard, mouse and text events on a virtual clock; without it, it is the client on
the system clock. notes/testmode.md.

Since Patella-Modern issue #19 both carry the Vulkan engine (notes/vulkan.md; option `PATELLA_VULKAN`, default
ON; `cmake/Vulkan.cmake`): src/vulkan/SurfaceVulkan.cpp on the back end `patella_render_vulkan`
(src/vulkan/Renderer.cpp and Quads.cpp) and the libraries' `patella_vulkan_deps` (volk, vk-bootstrap, VMA), the
shaders compiled by a glslang built in the tree; Vulkan-Headers, volk, VMA, vk-bootstrap, glslang and the CPU
driver (Mesa 26.2.5's lavapipe) are pinned by URL and SHA256 and downloaded on the first configure of a build
tree (about 85 MB). The CPU driver's `vulkan_lvp.dll` and `lvp_icd.x86_64.json` are copied next to Patella.exe,
PatellaTest.exe and `tests_vulkan.exe`. The engine runs only when the environment variable `PATELLA_VULKAN` is
`auto`, `gpu` or `cpu`, in place of engine 2 (DirectX 9); otherwise the client is as before. The preset's CTest
has two more tests: `tests_render` (src/vulkan/Quads.cpp, on every product preset) and `tests_vulkan` (the back
end headless on the CPU driver and the GPU, no window; skipped without a Vulkan loader). `-DPATELLA_CLIENT=OFF`
(the hosted CI) builds none of the engine and downloads nothing.

Run either Patella.exe (or PatellaTest.exe) only from a folder with copies of the data files (Tibia.dat, Tibia.spr, Tibia.pic, Tibia.cfg; for
example build\run), never from the root: the client rewrites Tibia.cfg on exit, and the root's data files
may be the user's own.

## Test server

A local 7.72 server (C:\Tibia\gameserver, not in the repository) that both clients log into (issue #18):
`python -I tools/testserver.py start` / `stop` start and stop it (only a server it started is stopped),
`tools/patch_client.py`
points copies of Tibia.exe and Patella.exe at 127.0.0.1 with the server's RSA key, and
`tools/login_client.py` logs a client in (account 772001, password patella), enters the game and logs
out, from build\run-orig or build\run-patella. Everything, including the server's configuration and
backup: notes/testserver.md.

`python -I tools/compare_traffic.py` (issue #19) plays a scripted session (walk, talk, look, containers,
use, trade, logout) with both clients against that server through a recording proxy (tools/proxy.py,
which decrypts with the server's key), replays each recording to both clients and compares their packets,
their state in memory after every step and their Tibia.cfg: notes/traffic.md. `--patella <exe>` tests another
Patella.exe (build\oracle-x86\Release or, from issue #5, build\windows-x64\Release). tools/client_state.py
reads Patella.exe's globals and field offsets from its PDB by name (issue #6), x86 or x64;
`python -I tools/client_state.py --layout <Patella.exe>` checks them without a client (for x86: every one
equal to the original's).

`python -I tools/compare_files.py` (issue #21) compares the files both clients write after the same sessions
(Tibia.cfg after the option dialogs, the automap files after a walk over three floors, a saved channel,
error.txt after forced errors and the error report flow, the files a patch from the login server writes):
notes/written-files.md. Its live recording is also Tibia.exe's walk run, the walk is 19 actions from a ladder
(Patella-Modern issue #16; `--check-route` checks it against the server's map), and the second Tibia.exe run is
`--repeat`. It takes `--patella <exe>` too and reads the dialogs' controls through client_state.py's
PDB table; tools/patch_client.py patches x86 and x64 images (Patella-Modern issue #15).

`python -I tools/compare_rendering.py` (issue #20) compares what both clients draw: issue #19's session
replayed with each engine (DirectX 5, DirectX 9, OpenGL), windowed and fullscreen, every frame read from the
engine's own surfaces by a DLL the run folders' copies import (tools/capture/patcap.c, no display needed),
with time made virtual so both clients draw the same moment: notes/rendering.md. It takes `--patella <exe>`
too, x86 or x64 (Patella-Modern issue #18): the capture DLL has the client's bitness (build\oracle-x86\Release\patcap.dll
for Tibia.exe and a 32-bit Patella.exe, build\windows-x64\Release\patcap.dll for the x64 one), and `add_import`
patches PE32 and PE32+ images.

`python -I tools/testmode_check.py` (Patella-Modern issue #21) runs the test build, PatellaTest.exe, twice with
the same input script (tests/testmode/login-walk.script: login, a square walk, a said line, logout) against that
server through tools/proxy.py and compares the runs' client packets, raw frames, driver logs and Tibia.cfg;
nothing drives the window from outside, and the client drops the desktop's own input: notes/testmode.md.

Every GUI comparison (traffic, files, rendering, network) empties its run folders before each run, down to the
data files and the patched client, and a second Tibia.exe run (orig-repeat) has a folder of its own
(Patella-Modern issue #12; notes/decisions.md "Clean run folders for the GUI comparisons (issue #12)").

Limits of the GUI comparisons until M2's built-in test mode replaces them (Patella-Modern issue #13):

- **Keep off the mouse and the keyboard while one runs.** They drive real client windows with posted window
  messages, and real input reaches the same windows: a mouse move or click over a client window comes in
  between the posted ones, a key goes to the client that has the focus. On November 2 a click during a
  rendering run crashed Tibia.exe (error.txt: "Debug Assertion 7.72 GUI.cpp 1633", "Capture==NULL", from
  MainFrm.cpp 568 at the point (2873,1375): TWindow::SetCapture asserts that no window holds the mouse
  capture, and a button went down while another click still held it), and the run's
  leftovers spoiled the following runs (since issue #12 every run starts from an emptied folder, so only the
  run that was disturbed fails). Start a comparison and leave the desktop alone until it ends; a run that
  failed while someone used the desktop is not evidence about the clients: run it again.
- **compare_rendering.py's fullscreen runs need a 1024x768x32 desktop.** They use the desktop's own mode so
  that no display mode really changes (FULLSCREEN_MODE, notes/rendering.md), and the script refuses them in any
  other mode before it starts a client, for example on the 5120x1440 desktop: "the desktop is in (5120, 1440,
  32, 120), not (1024, 768, 32): the fullscreen runs would change the display mode". On such a desktop run
  `--modes windowed`; the fullscreen runs need the 1024x768 the display falls back to with the monitor off
  (notes/testserver.md). Decision D11 (notes/modernization-plan.md: a borderless window at the desktop's
  resolution instead of exclusive display modes) removes the mode change, and with it this limit, later.

## Checking

- Code style (issue #8): `.clang-format` describes the style of src/ (tabs of four columns, function bodies
  on their own line, no column limit; the arguments of TASSERT*, TERROR* and TEND* are whitespace-sensitive,
  so clang-format never touches them), `.clang-format-ignore` leaves src/Extern and tools/ alone,
  `.editorconfig` sets tabs, LF and UTF-8 for every editor. With Visual Studio's clang-format 22
  (`VC\Tools\Llvm\x64\bin`): `clang-format --dry-run --Werror src/*.cpp src/*.h src/compat/*.h
  src/testmode/*.cpp src/testmode/*.h src/vulkan/*.cpp src/vulkan/*.h src/res/resource.h tests/unit/*.cpp
  tests/vulkan/*.cpp` reports nothing; `clang-format -i` on a changed file formats it. Hand-laid tables (case
  tables, vertex and pixel format lists) and the macros clang-format cannot parse sit between
  `// clang-format off` and `// clang-format on`.
- clang-tidy (issue #8): `.clang-tidy` has the checks of the coding standard (notes/modernization-plan.md,
  section 8). Run it only through `python -I tools/tidy.py -p <build dir> [--fix] <files>` (the build dir
  needs compile_commands.json: CMAKE_EXPORT_COMPILE_COMMANDS; default build\windows-x64, the preset of
  issue #5; for an x86 build's commands add `--extra-arg=-m32`). It lists the findings outside the
  TASSERT*/TERROR*/TEND* arguments with a count per check and counts the ones inside apart (they wait for
  M5); with `--fix` it reverts, character by character, every fix clang-tidy made inside such an argument,
  in the file and in the headers it changed (plan 4.2). Never run `clang-tidy --fix` directly.
  `--all` takes every source of compile_commands.json under src/ (not src/Extern).

- How the tests report failures and crashes (issue #23): a test program that fails ends with a
  non-zero exit code and its report, and CTest lists the test as failed (a build step that fails stops
  the build with the compiler's output); a passing run ends with `100% tests passed`. Before each
  test the child writes the test's name into memory shared with the parent (the `#define
  TestX(...)` lines before `main` in difftest.cpp: a new test needs one) and runs `_heapchk()` after
  it. A crash prints `crash:` lines in the child where it can (access violations, stack overflow,
  heap corruption with address and stack; uncaught C++ exceptions with the thrown type and the
  message of a TMyException or std::exception; terminate, abort, invalid parameter, pure call,
  /GS cookie), and the parent always prints `difftest: the test process ended with exit code
  0x... (name) in TestX` (or "in the heap check after TestX"), also for `__fastfail`, which nothing
  in the child can catch. The child runs in a job that dies with the parent (no orphan keeps
  difftest.exe locked) and never waits on Windows Error Reporting; DIFFTEST_TIMEOUT=<seconds>
  (default 1800, 0 none; CTest stops difftest and communicationtest after 7,200 s) stops a hung child.
