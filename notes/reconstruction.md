# Reconstruction guide

How a source file of Tibia.exe 7.72 is turned into `src/<File>.cpp`. `src/Network.cpp` is the
reference example.

## Inputs

Since November 2, 2026 the decompilation workspace below (`symbols.tsv`, `names.tsv`, `file-ranges.tsv`,
`decomp/`, `notes/source-map.md`, the analysis tools triage.py, simplify.py, callcheck.py, ehinfo.py,
ehcompare.py, xctable.py, listing.cmd, and `rea-out/`; lines.py too until issue #74, which dropped it with error.txt) is not in the repository: it is kept,
gitignored, in `decompilation/`; `tools\decompilation.ps1 -Restore` puts it back at these paths before
analysis work, `-Stash` puts it away (CLAUDE.md). The last commit that has the files is e02adfa.

| File | What it is |
|---|---|
| `symbols.tsv` | Every function: address, size, kind, source file, assertion lines, catch-block parent, parameter names. Generated by `tools/triage.py`. |
| `names.tsv` | Hand-maintained names: address, name, kind, confidence, note. Add a row for every function you name. |
| `decomp/clean/<File>.c` | Readable pseudocode for one source file. Generated by `tools/simplify.py`; rerun it after editing `names.tsv`. |
| `decomp/raw/functions/<address>.c` | Raw Ghidra output, when the clean copy hides something. |
| `notes/source-map.md` | Which functions belong to which file, and the unresolved gaps. |

Regenerate after changes: `python -I tools/triage.py` (only when the raw decompile changes), then
`python -I tools/simplify.py`.

## Reading the clean pseudocode

- `TASSERT_FAILED(line, "expr", "name", value)`: a failed assertion with one value, written
  `PATELLA_ASSERT_VALUES(expr, name)` (TASSERT1(line, expr, name) until issue #79). The expression text is the
  original source text; the line is the original's (issue #35), which the source no longer names.
- `TERROR(line, "message", "name", value)`: `TERROR1("message", name)` (TERROR1(line, "message", name) until issue
  #80; the line is the site's own source location now).
- After most functions come three catch blocks, the original's catch wrapper around the body: a 20-byte
  one re-throws a `PROGRAM_ERROR` (ours: a `TProgramError`, issue #80), a `TRETHROW(line, "names"...)` one and a `TERROR(line, "unknown exception
  occurred", ...)` one wrap the exception with the line and the function's parameters (or expressions of
  them). The reconstruction does not write them (src/common.h; until Patella-Modern issue #78 they were the
  macros TBEGIN and TEND, TEND1, TEND2): the function's comment names their line, and an exception passes to the
  first handler that really handles it.
- A catch block with its own message, such as "Symmetric encryption failed with unknown
  exception", is an inner `try { ... } catch (...) { TERROR("..."); }`.
- Get the catch types and the try ranges from the exception tables, not from the pseudocode:
  `python -I tools/ehinfo.py <address>`. The standard trio is `PROGRAM_ERROR`, `TMyException &`,
  `...`. If the wrapper's try block starts at a state above 0 (for example `try states 5-5`), the
  assertions that build the first states come before it; a failure there was not wrapped with
  "exception occurred" (the order of the assertions and the body follows the binary all the same). Each assertion builds five strings, so five states.
- Ghidra hides the `this` pointer of member calls (`in_ECX`). When it matters which object a
  call uses, read the instructions: `rea instructions C:\Tibia\Patella\Tibia.exe <address>
  --provider ghidra --snapshot rea-out\tibia.snapshot --json` (after `-Restore`; upstream's is
  C:\Tibia\Patella\rea-out) and look for `MOV ECX, <address>`
  or `LEA ECX, [EBP + ...]` before the call.
- Return values of small wrappers are often dropped by Ghidra (`void FUN_...` that returns
  `EAX` from a callee). Check the callers.
- Inlined string functions appear as copy loops (`strcpy`, `strcat`, `strlen`, `memset`).
- Static constructors are not found by Ghidra. They sit near `0x559fc0`; disassemble them with
  `objdump -d -M intel --start-address=0x559fc0 --stop-address=0x55a400 Tibia.exe`.

## Writing the source

- One `src/<File>.cpp` and `src/<File>.h` per original file, with the original file name.
- Functions in original source order: sort by assertion and catch line numbers, not by address.
  Functions without line evidence go where the binary puts them.
- Before each function: `// 0x<address>, lines <first>-<last>` and a short note only when the
  behaviour is not obvious.
- Names: keep every name the binary gives (parameter names from catch blocks, identifiers in
  assertion strings such as `CurrentServer`, `NUMBEROFSERVER`). Invent names only for the rest,
  in the original style: TitleCase free functions, `T`-prefixed classes, TitleCase members.
- Globals: in an anonymous namespace unless another file uses them (issue #44; misc-use-anonymous-namespace in
  .clang-tidy), ordered by address, each with its address; a run of them between external globals gets a
  `namespace {` of its own, so the order stays. A file-scope `static` stays only where the namespace moves the
  images' data (MSVC orders a translation unit's globals by their decorated names): GUI.cpp's Hotkeys, Talk.cpp's
  TemporaryIgnoreList and IgnoreList and TRSA.h's HeaderExponent, each with a NOLINT or comment saying so; compare
  the images. The PDB names data in an anonymous namespace by its plain name (client_state.py finds it as before),
  functions as `` `anonymous namespace'::Name ``.
- Every file is reconstructed, so every declaration lives in the header of the file that defines
  it (`src/external.h` held the declarations of files not reconstructed yet; it was removed in
  issue #14). A new declaration goes into its owner's header with its address; a header includes
  the headers whose types it uses, a .cpp the headers of the functions and data it uses (no
  catch-all header). Watch the include cycles noted in notes/progress.md.
- Data defined in a header with internal linkage has one copy per including object in the binary:
  the text table (`src/Text.h`, every .cpp that reads a text includes it; Dialogs.h too, for its
  inline code) and graphics.h's DefaultFontColor. An object's code reads only its own copy.
- Constants are `inline constexpr int` in a header (`constexpr` in a .cpp), not `#define` (issue #36);
  a macro only where the preprocessor needs one (`#if`, configuration such as `DIRECT3D_VERSION`, the
  resource IDs of `src/res/resource.h`, an API's own macro names such as SurfaceGL.cpp's `WGL_*_ARB`).
- Every enum has an explicit underlying type, followed by static_asserts of its size and of
  `std::underlying_type_t` (issue #37); a new enum is an `enum class` unless its values are used as
  ints (array indices, bit numbers, int fields, packets) or its enumerators appear in a TASSERT/TERROR
  argument.
- A class whose destructor frees what it holds (memory, a FILE *, a descriptor, its children) declares its
  copy constructor and copy assignment `= delete`, or defines them where the code copies it (vlong's shared
  value) (issue #34). An empty special member is `= default` when it is defined outside the class (it stays
  user-provided); inside the class only where that changes neither the image nor value-initialization
  (issue #34; since issue #47, with the oracle gone, TXTEA's destructor is `= default` too; TSurfaceDX left with
  #94). A class that overrides and that nothing derives from is `final` (issue #47), unless the golden tests put
  objects of their own where our code expects it (a redirected constructor, a stand-in passed as its type) or
  redirect a member function that `final` lets the compiler inline; such classes are listed in
  notes/decisions.md, "#47".
- A local that is not changed is `const` (values, references, and what a pointer points to), and a member
  function that changes no member of its object is `const` (issue #39; misc-const-correctness and
  readability-make-member-function-const in .clang-tidy). `const` goes first (`const int`, `const T *`), also
  where clang-tidy's fix writes it after the type. A local stays non-const, with a NOLINT and the reason, where
  const changes the image (a constant the compiler then folds, as in TTalkBuffer::Remove; until issue #94 the
  oracle's image was the one that mattered): compare the images. A virtual function becomes const only together with all its overriders.
- A pointer parameter whose pointee the function only reads points to const (issue #50;
  readability-non-const-parameter in .clang-tidy, which looks at pointers to integers and floating types). The
  declaration in the header changes with the definition, and so does a golden test's fake of the same function
  (tests/golden/commworld.cpp's F_ functions). A callback whose type an API fixes (Windows, MFC, qsort, Vulkan)
  and a virtual function without all its overriders keep their parameters.
- A cast that is not a plain arithmetic conversion or upcast is a named cast (issue #41;
  cppcoreguidelines-pro-type-cstyle-cast in .clang-tidy), the one the C cast would have been: static_cast for a
  downcast and for `void *` to `T *`, const_cast to drop const, reinterpret_cast for integers to pointers and back
  (`INT_PTR` message parameters), unrelated pointers and function pointers. A downcast whose static_cast does not
  compile (an incomplete class) would be a reinterpret_cast as a C cast: check, do not guess.
- No `goto` (issue #42; cppcoreguidelines-avoid-goto in .clang-tidy), except where the binary has one shared exit
  block that a loop's end and a jump from inside it both reach and C++ has no other way out (ProcessEvents' `goto
  Done`, block 0x44a2f5): such a goto carries a NOLINT naming the block. Code the binary reaches from several
  branches (a copy, a skipped draw) is written with a value that says which (a skin of 0, an Index of -1) and an
  if; compare the images and replay the golden corpus, since the generated code usually changes.
- No strcpy, strcat, sprintf, vsprintf or gets in src/ (issue #57; `tools/banned_calls.py`, a job of the hosted
  CI). A text buffer of the original (`char Name[30]`) is a `TFixedString<30>` (src/types/FixedString.h: exactly
  the array, converting to `char *` as it decayed) and is written with Assign, Append, Format and AppendFormat
  (std::format's language; std::format_to_n on the product presets, the C++17 stand-in of src/compat/format.h in
  the oracle); a buffer known only by a pointer is written through `TStringBuffer(Pointer, Size)`, with the size
  its callers allocate (say where it comes from). The writes put the text and its NUL where the C function did and
  nothing else; a text that does not fit (an overflow in the original) is cut at N - 1. A frozen structure's
  member becomes a TFixedString only with static_asserts of its size and offsets (under PATELLA_ORIGINAL_LAYOUT,
  in the .cpp, where it has pointers or a vtable). Keep the array where a TASSERT/TERROR argument needs it as
  a `std::string` (TERROR_REASON's reason: Script.cpp's Filename, until M5), and pass `.Chars` where it goes
  through `...` (MsvcSnprintf, a test's Logf): a TFixedString there is its N bytes, not a pointer. A bounded
  `MsvcSnprintf(Fixed.Chars, sizeof(Fixed), ...)` stays (_snprintf's result and missing NUL; the text table's
  runtime formats). A constant format whose text always fits is a Format (issue #64: Help.cpp's help texts, the
  map messages, the account number and the dotted address); one that can fill the buffer or formats a double
  (Control.cpp's frame rate: printf and std::format write NaN differently) stays MsvcSnprintf.
- A pointer and its length go as one span (issue #59): `patella::TSpan<T>` or `TSpan<T, N>` of src/compat/span.h
  (std::span on the product presets, a C++17 stand-in in the oracle; spell the type, there are no deduction guides in
  the stand-in). Where a TASSERT/TERROR argument names the original's parameters, the body defines them as
  locals from the span (`uint8 *const data = Bytes.data(); const int size = static_cast<int>(Bytes.size());`), so
  the text stays and a null pointer or a size above INT_MAX fails as before. A C string whose null pointer an
  assertion reports, or whose end is its NUL, stays `const char *`.
- No C arrays (issue #60): a member, global or local array is `std::array<T, N>` (nested for the original's
  `T[X][Y]`: `std::array<std::array<T, Y>, X>`), a text `TFixedString<N>`. A frozen structure's array changes only
  with static_asserts of the structure's size and the member's offset (the original's, from the oracle's PDB;
  unconditional where the structure has no pointers, else under PATELLA_ORIGINAL_LAYOUT). Where the array decayed
  to a pointer, `.data()` (a TFixedString: `.Chars`, also for `...` and for a span); an array a TASSERT/TERROR
  argument needs as a pointer or a `std::string` stays until M5, with `NOLINT(modernize-avoid-c-arrays)` and the
  reason on its line. tools/client_state.py reads a `std::array<T, N>` member as `T[N]`.
- No `FILE` and no fopen, fclose or printf family in src/ outside src/types/File.h (issue #64; the same
  `tools/banned_calls.py`). A file is a `TFile`: exactly a `FILE *` (a frozen member keeps its 4 bytes; Script.h's
  four classes assert it), closed by its destructor, compared with nullptr and NULL as the pointer was (TASSERT
  texts); Open(Name, TAccess::Read/Write/Append, TContent::Binary/Text) is fopen with its result (false, errno),
  and the reads and writes are the C functions' with their results: the callers raise their own errors, as before.
  TContent::Text writes every '\n' as "\r\n" on every platform (the Microsoft C runtime's own text mode on
  Windows, a translating stream elsewhere), so a file the original opened with "t" or no letter keeps its bytes;
  Print is fprintf with std::format's language (check that each conversion gives the same characters). stdout's
  printf is compat/print.h's `PrintLine`; not std::print, which throws where the write fails (a GUI program has no
  stdout). The standard streams' own writes (the test mode's fputs to stderr) are not files and stay.
- Who owns each heap object is in notes/ownership.md (issue #58): a new allocation gets its line there. An owning
  pointer that is the only owner, released with the matching `delete`/`delete[]`, whose pointee's destructor cannot
  throw, is a `std::unique_ptr<T>` (`<T[]>`) with the default deleter: the original's `delete` stays an explicit
  `reset()` at the same place and in the same order, its `new` a `reset(new ...)` (not `make_unique`, which
  value-initialises), a clear without a free a `release()` whose result is dropped, a store over a block still held
  (the original's leak) a dropped `release()` before the `reset(new ...)`; a frozen structure's member only
  with static_asserts of its size and offset under PATELLA_ORIGINAL_LAYOUT, and the file asserts `sizeof`/`alignof` of
  the `unique_ptr` against the raw pointer. Pass `.get()` where a raw pointer is needed (and through `...`, where a
  `unique_ptr` must never go). Everything a window, the event queue or a container owns, everything whose destructor
  may throw (`TComponent`, `TTalkBuffer`: `reset()` is `noexcept`), and the mismatched releases stay raw; ownership.md's
  section 7 lists every raw owner with the milestone that unblocks it.
- Use the error macros exactly where the binary has the corresponding blocks: `PATELLA_ASSERT(expr)` and
  `PATELLA_ASSERT_VALUES(expr, value[, value])` (`src/compat/assertion.h`, issue #79: no line argument, the
  assertion's own source location; TASSERT* until then) and `TERROR*` (`src/common.h`; since issue #80 without the
  original's line, the site's own source location); the catch wrappers are not written (above), a handler of the function's own (its own
  message or recovery) is. A thrown error code is `throw TProgramError{PROGRAM_ERROR::...}` (the original throws the
  bare enum; issue #80), caught as `const TProgramError &`. A failure the caller recovers from may be returned as
  `patella::TExpected<T, TError>` (`src/compat/expected.h`, issue #80) behind the function the original exposes,
  which still throws (Script.cpp's TryOpen behind open).
- Behaviour must match the binary exactly, including odd behaviour (for example
  `ConnectToGameServer` connects even when `CreateSocket` failed). Note such cases in a
  comment; do not fix them.
- Tabs for indentation.

## Building

The build is CMake (3.30 or newer) with Ninja: `CMakeLists.txt`, `CMakePresets.json`, `cmake/*.cmake`. The
MSBuild project (`Patella.sln`, `Patella.vcxproj`) and the .cmd/.ps1 scripts are gone since issue #10; every
step they did is a CMake target, a CTest test or a Python tool now (notes/decisions.md, "Removing the Visual
Studio project and the scripts (issue #10)"). The MSVC presets mark their architecture and toolset
`external`: CMake does not set up the compiler. `tools/build.py` does it (vcvarsall.bat for the preset's
architecture, found through vswhere) and runs the workflow, from any shell:

```
python -I tools/build.py windows-x64             # the x64 client and the unit tests, Release
python -I tools/build.py windows-x64-debug       # the same, Debug
python -I tools/build.py windows-x64-asan        # windows-x64 under MSVC's AddressSanitizer (-debug: Debug)
python -I tools/build.py windows-x64-gcc         # the unit tests with mingw-w64 GCC 16 (-debug: Debug)
python -I tools/build.py linux-x64-gcc           # patella_core, the unit tests, golden_runner, GCC 16 (Docker on Windows)
python -I tools/build.py linux-x64-clang         # the same, Clang 22 with ASan and UBSan (-debug: Debug)
python -I tools/build.py capture-x86             # only patcap.dll, the 32-bit capture DLL for Tibia.exe
python -I tools/build.py --list                  # the workflow presets
python -I tools/build.py windows-x64 --fresh     # extra options go to cmake --workflow
python -I tools/build.py --env windows-x64 cmake --build --preset windows-x64-debug   # any command, in the
python -I tools/build.py --env windows-x64 ctest --preset windows-x64 -R golden       # preset's environment
```

There is no 32-bit client build since Patella-Modern issue #94 (M6, November 6, 2026): the preset `oracle-x86`
(issue #4) built the reconstructed client for x86 with the former Patella.vcxproj's options, the differential tests
(difftest, sysinctest, communicationtest, vlongtest), the SafeSEH gate (issue #89), the golden corpus's recorder
and the mfc_shim compile check, and checked the resources and imports against Tibia.exe (compare_resources.py,
compare_imports.py). It left the fork with the engines DirectDraw, Direct3D 9 and OpenGL and the x86 layout
asserts; it is in upstream Patella and at this repository's tag `layout-frozen-final` (ee1705c), the last commit with
it (notes/decisions.md, "The oracle retired (issue #94)"). What it checked is checked now by the frozen golden corpus
(function results, by value), the reference recordings and the live comparisons (tier A), and the unit tests.

In the Docker image (issue #91) build.py mounts the golden corpus read-only at `/golden` and sets PATELLA_GOLDEN_DIR
there to it: the host's PATELLA_GOLDEN_DIR, else the repository's build\golden when it exists (`PATELLA_GOLDEN_DIR=none`:
no corpus, golden is skipped as in hosted CI), and passes the time zone of the corpus's MANIFEST.tsv as TZ (issue #93:
UTC0; the runner sets it itself too); without a manifest, Windows' zone as before (POSIX form, from
GetTimeZoneInformation; TZ itself when set), for a corpus recorded before #93 in the machine's zone.
PATELLA_GOLDEN_UNVERIFIED of the host goes in too:

```
set PATELLA_GOLDEN_DIR=C:\Tibia\Patella-Modern\build\golden
python -I tools/build.py linux-x64-gcc           # golden replays it in the image (and golden_concurrent)
python -I tools/build.py linux-x64-clang         # under ASan and UBSan
```

`import std;` (issue #113, M7; `cmake/ImportStd.cmake`): the option PATELLA_IMPORT_STD, ON in the presets windows-x64
(and windows-x64-asan), windows-x64-gcc, linux-x64-gcc and since issue #121 linux-x64-clang, sets CMake's experimental gate
(CMAKE_EXPERIMENTAL_CXX_IMPORT_STD, a UUID per CMake minor version: 4.1 and 4.4 are known) before project() and
requires the compiler's std module; `patella_target_import_std(<target>)`, after the target's language, warning and
hardening settings, lets a target's sources import it and gives the std module the target's options. Its one user is
tests_import_std (tests/unit/import_std_test.cpp). linux-x64-clang (issue #121): the image's Clang 22 uses GCC 16's
libstdc++ (Debian's libstdc++ 14, which has no std module, until then), and on Clang the target and its std module
are compiled without _FORTIFY_SOURCE (glibc's Clang wrappers of the printf family cannot be exported). On a CMake version without a known gate the configure warns and builds without it. Per compiler, the
errors and what would unblock Clang: notes/decisions.md, "import std (Patella-Modern issue #113, M7)". A build folder
configured before #113 fails its configure ("Experimental `import std` support not enabled when detecting toolchain"),
because the compiler was detected without the gate: configure it once with `python -I tools/build.py <preset> --fresh`.

SDL3 (issue #122, M8; `cmake/Sdl3.cmake`): windows-x64 and its variants fetch SDL 3.4.18's release archive (pinned by URL
and SHA256, like cmake/Vulkan.cmake's libraries) at the first configure and build it into build\<preset>\_deps as a static
library with the client's CRT; nothing is installed. The client runs on SDL3's window and event loop by default and on
MFC's with `PATELLA_WINDOW=mfc` in its environment, until the MFC removal (issue #127); the start-up log says which
(`[info] window: SDL3`). The Linux presets do not use SDL3 yet (notes/decisions.md, "#122").

No warnings on any preset (plan section 4.1): the product presets and capture-x86 build with /WX or -Werror, and
`tools/build.py` fails a warning besides (issue #17; it was what failed the oracle, which kept /WX-). It passes
cmake's output through and scans it, up to the test step, for compiler, resource compiler, assembler and linker
warnings (MSVC's `warning C4101`, `warning LNK4075`, `warning RC4005`, `warning A4018`, `Command line warning
D9025`; GCC's and Clang's `file:line:col: warning:`); after a run that warned it lists them again (`build.py: 1
warning in the build ...`) and exits 1, even when cmake succeeded. That holds for every workflow and for `--env
<preset> cmake ...`. Ninja compiles only what changed, so an up-to-date build shows no warnings; `--fresh`
checks every file. Plain `cmake --workflow` from a developer prompt does not check.

From a developer prompt for the right architecture (`vcvarsall.bat x86` for capture-x86, `x64` for windows-x64) the
plain CMake commands do the same: `cmake --workflow --preset <name>`, or step by step `cmake --preset windows-x64`,
`cmake --build --preset windows-x64` (windows-x64-debug: Debug), `ctest --preset windows-x64`. Everything needs Visual Studio
2026 with the C++ workload and the MFC component (MSVC 14.51), Python 3.13 on PATH and Tibia.exe in the root
(or the cache variable PATELLA_TIBIA_EXE): the resource pictures are extracted from it at configure time
(cmake/Resources.cmake, notes/resources.md).

The preset `capture-x86` (Patella-Modern issue #94; `cmake/Capture.cmake`, CMakeLists.txt's PATELLA_CAPTURE) is a
test instrument: it builds only build\capture-x86\Release\patcap.dll, the 32-bit capture DLL that
tools/compare_rendering.py and the reference recordings' record step (tools/reference_record.py) load into Tibia.exe
(the scripts build the target themselves when the DLL is missing or older than tools/capture/patcap.c), with the
options of the former build-capture.cmd (/W4 /WX, the static CRT, no manifest; CMake's Release /O2). Tibia.exe's only
since issues #92 and #94: patcap.c does not build for x64, and the 32-bit oracle's Patella.exe that it captured too is
gone. No client, no tests, no header checks; its workflow configures and builds.

The product presets (windows-x64, issue #5; linux-x64-gcc and linux-x64-clang, issue #7) give their targets
the settings of `cmake/Warnings.cmake` and `cmake/Hardening.cmake` (issue #8):

- `patella_target_language(<target>)`: C++23 (`/std:c++latest` on MSVC, `-std=c++26` on GCC and Clang),
  `/permissive- /Zc:__cplusplus /utf-8 /Zc:preprocessor /Zc:inline`, no `/Zc:strictStrings-`; C17 for the C
  sources on GCC and Clang (the regexp's K&R definitions are not C23, GCC 16's default).
- `patella_target_warnings(<target>)`: `/W4` (GCC and Clang `-Wall -Wextra -Wpedantic -Wconversion
  -Wshadow`) per source, `/W3` (`-Wall`) for the files on the compiler's baseline list in Warnings.cmake
  (`PATELLA_WARNING_BASELINE_MSVC`, `_GCC`, `_CLANG`; a file is on a list when its translation unit warns,
  wherever the warning is), and warnings as errors (`COMPILE_WARNING_AS_ERROR`; `cmake
  --compile-no-warning-as-error` turns it off to measure). Headers in angle brackets are external to MSVC
  (`/external:anglebrackets /external:W0`). Clang's warning about K&R definitions
  (`-Wdeprecated-non-prototype`, on at every level) is off for C. A file leaves a list when it builds clean at
  the full level; the lists only shrink. On every C++ source, the baseline files included (issue #38): the
  unused-entity warnings (MSVC `/w34100 /w34189 /w34505`, GCC and Clang `-Wunused -Wunused-parameter
  -Wunused-but-set-parameter`) and the implicit-fallthrough warning (GCC `-Wimplicit-fallthrough=5`, which
  takes only the attribute, not a comment; Clang `-Wimplicit-fallthrough`; MSVC has none). A parameter that is

- **They run on the desktop of the session they are started in (Patella-Modern issue #56).** For a run that no
  one's mouse and keyboard may reach, start it in a second interactive session ("Checking", "The live checks in a
  second session"). `--hidden` (every live tool; tools/desktop.py; experimental) runs the tool on a hidden desktop
  of its own instead, where most results differ: DirectDraw and Direct3D 9 do not start (Tibia.exe and the oracle
  fall back to OpenGL), the Vulkan CPU driver's first present fails (PATELLA_VULKAN=cpu: the client crashes after
  1 s), and GetCursorPos fails (the posted clicks of compare_traffic.py and compare_files.py miss). What gives the
  same results there: PatellaTest.exe on a GPU (`reference.py compare --vulkan gpu --hidden`), the OpenGL engine
  (`compare_rendering.py --engines gl --hidden`) and compare_network.py. notes/decisions.md, "The live checks on a
  hidden desktop".
- **Keep off the mouse and the keyboard while one runs.** They drive real client windows with posted window
  messages, and real input reaches the same windows: a mouse move or click over a client window comes in
  between the posted ones, a key goes to the client that has the focus. On November 2 a click during a
  rendering run crashed Tibia.exe (error.txt: "Debug Assertion 7.72 GUI.cpp 1633", "Capture==NULL", from
  MainFrm.cpp 568 at the point (2873,1375): TWindow::SetCapture asserts that no window holds the mouse
  capture, and a button went down while another click still held it), and the run's
  leftovers spoiled the following runs (since issue #12 every run starts from an emptied folder, so only the
  run that was disturbed fails). Start a comparison and leave the desktop alone until it ends; a run that
  failed while someone used the desktop is not evidence about the clients: run it again.
- **compare_rendering.py's fullscreen runs need a 1024x768x32 desktop.** They use the desktop's own mode so
  that no display mode really changes (FULLSCREEN_MODE, notes/rendering.md), and the script refuses them in any
  other mode before it starts a client, for example on the 5120x1440 desktop: "the desktop is in (5120, 1440,
  32, 120), not (1024, 768, 32): the fullscreen runs would change the display mode". On such a desktop run
  `--modes windowed`; the fullscreen runs need the 1024x768 the display falls back to with the monitor off
  (notes/testserver.md). Decision D11 (notes/modernization-plan.md: a borderless window at the desktop's
  resolution instead of exclusive display modes) removes the mode change, and with it this limit, later.

## Checking

- The live checks' server start (Patella-Modern issue #68): every tool that needs the test server starts it through
  `testserver.py start`, which returns when both ports listen and the world is loaded. A server of its own that stalls
  or exits it stops and starts once more (the failed attempt's log kept as build\testserver\server-attempt<N>.log); a
  server or port someone else holds ends the start, untouched. So a cold or slow start needs no rerun by hand. A
  start that still fails says why in its `testserver start:` lines: look there first. The tools' own self-tests run
  without a server or a client: `python -I tools/testserver.py self-test`, `python -I tools/compare_files.py
  --self-test`, `python -I tools/testmode_check.py --self-test`.
- How the tools read a client (Patella-Modern issue #92, M6): Tibia.exe (and until issue #94 the oracle's 32-bit
  Patella.exe) through its memory (tools/client_state.py) and, for the frames and the virtual clock, tools/capture/patcap.c; the x64

  client through its test mode only". Self-tests: `python -I tools/testmode_client.py --self-test` besides the others.
- Code style (issue #8): `.clang-format` describes the style of src/ (tabs of four columns, function bodies

  so clang-format never touches them), `.clang-format-ignore` leaves src/Extern and tools/ alone,

  What Windows does to such a session (Windows 11 Pro, a client edition):
  - **One connected session at a time.** A workstation lets one user at a time use its desktop: a switch to the
    other user, or a Remote Desktop logon, disconnects the session that was connected (its programs keep
    running). The user therefore cannot work in their own session while the checks run in the second one; the
    second session keeps the checks' windows apart from the user's windows and input, not from the user at the
    machine. Remote Desktop to this computer itself (localhost) is no way around it: one session is connected at
    a time either way. Several connected sessions at once need Windows Server (Remote Desktop Services) or
    Windows Enterprise multi-session, not this edition (Microsoft Q&A, "by design Remote Desktop on a workstation
    will only allow one user at a time":
    https://learn.microsoft.com/en-us/answers/questions/383792/rdp-session-local-user-logs-off-when-the-remote-co).
  - **The checks' session must stay connected and unlocked for the whole run.** Of the interactive window
    station's desktops only one is the input desktop, the one visible to the user that receives input; the
    system switches to the Winlogon desktop on Ctrl+Alt+Del and the UAC prompt, and to the ScreenSaver desktop for
    a secure screen saver (Microsoft Learn, "Desktops",

    running (Microsoft Learn, tsdiscon,

    console with `tscon <session id> /dest:console` instead
